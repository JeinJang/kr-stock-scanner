# 로컬 일봉 이력 저장소로 돌파 신선도 데이터 소스 교체 — 설계

- **작성일:** 2026-08-20
- **상태:** 설계 승인 대기(스펙 리뷰용)
- **목적:** 돌파 신선도 지표의 입력을 **KRX 종목별 조회(종목당 6콜/일)**에서 **로컬 일봉 저장소(하루 2콜)**로 바꾼다. KRX의 2년 조회 상한과 로그인 세션 의존을 제거하고, 지금은 불가능한 10년 깊이의 판정을 가능하게 한다.

## 배경 / 문제

2026-08-19에 돌파 신선도 기능(A: 재돌파 간격, B: 갱신 깊이)을 넣었다. 입력은 `src/recency_source.py`의 `fetch_bars`가 로그인 KRX 클라이언트로 종목별 11년 일봉을 가져오는 방식이다.

실제 KRX에 붙여 보니 전제가 틀렸다.

- **KRX는 종목별 조회를 약 2년으로 제한한다.** 3년 이상을 요청하면 오류가 아니라 **빈 응답(LOGOUT)** 이 온다. 1년 244행, 730일 485행, 3년 이상 0행.
- 그래서 730일 청크로 쪼개는 수정을 넣었고 동작은 하지만, **종목당 6콜**이 든다. 하루 80종목이면 ISIN 조회까지 약 560콜이다. 2026-08-03에 IP/계정 차단을 당한 원인이 과다요청이었다는 점에서 편한 수치가 아니다.
- 로그인 세션 방식(`data.krx.co.kr` 웹 내부 엔드포인트)이라 스크래핑에 가깝고, 차단·세션 만료에 취약하다.

한편 이 저장소에는 이미 **KRX 공식 Open API 클라이언트**(`data-dbg.krx.co.kr/svc/apis`, AUTH_KEY 인증)가 있고 `KRX_API_KEY`도 설정돼 있다. 이쪽은 종목별 조회가 없는 대신 **일자별 전 종목 벌크**를 제공한다.

## 스파이크 실측 결과 (2026-08-20, 완료)

버리는 코드로 실제 측정했다. 이 설계의 근거는 전부 아래 수치다.

**처리량**
- 순차 호출: 콜당 1.87초 → 11년치 약 3시간.
- **동시 8 요청: 콜당 0.24초, 716건 연속 요청에서 실패 0건.** 일일 호출 한도로 보이는 제약은 나타나지 않았다.
- 1.4년치 실적재: 921,253행 / 333 거래일 / 2,883 종목 / **1.9분 / 96MB**(10개 컬럼 기준).
- **11년 실측(2026-08-20 백필 완료): 5,740 요청 / 5,392 거래일 적재 / 6,481,499행 / 12.1분 / 742MB.** (스파이크 당시 추정치는 약 16분 / 약 780MB.)

**과거 데이터 도달 범위**
- `sto/stk_bydd_trd`가 `basDd=20150102`에서 899행, 고가 필드 포함. 11년 전도 정상 반환.

**수정주가**
- 이 API는 **원주가**를 준다. 삼성전자 2018-05-02 종가 2,650,000 → 05-04 종가 51,900 (50:1 액면분할 미소급).
- **보정 계수는 이 피드만으로 정확히 유도된다.** `기준가 = 당일 종가 − 전일대비`이고, 정지 전 종가와 비교하면 계수가 나온다. 링크드 5:1 병합에서 정지 전 종가 396 × 5 = 재개일 기준가 1,980, **오차 0**. 상장주식수 비율(66,844,667 → 13,368,933)도 같은 값을 가리킨다.
- 1.4년 구간에서 `|계수−1| > 2%` 이벤트 537건. 계수 5·10(액면분할/병합) 304건, 무상증자 권리락(계수 1.8 등), 주식배당(계수 1.05) 35건으로 전부 설명된다.
- **현금배당락은 오검출되지 않는다.** 12월 결산 상장사가 수백 곳인데 20251229 검출이 10건뿐이다. KRX가 현금배당락에는 기준가를 조정하지 않기 때문이며, 검출기가 깨끗하다는 강한 증거다.

**판별 정확도 대조 (2026-08-19 기준)**
- 자체 판별 15종목 vs 저장된 investing 결과 16종목, **교집합 13**.
- investing만 3종목 중 **2종목(대신정보통신·링크드)은 실제로 신고가가 아니다.** 둘 다 5:1 액면병합 후 재개일이고, investing이 병합을 소급 반영하지 않아 생긴 거짓 신고가다. 즉 **현재 운영 중인 스캐너는 액면병합 종목마다 거짓 신고가를 보고해 왔다.**
- 나머지 1종목(평화산업)은 창 길이 차이다. 오늘 고가 1,077, 250 거래일 최고 1,081(미달), **365 달력일 최고 1,077(동률 → 신고가)**. 250 거래일은 달력 376일이라 52주보다 11일 길다.
- 우리만 잡은 2종목은 investing 목록 잘림(`total > 취득` 경고, 페이지네이션 미구현) 또는 종가 기준 차이로 보인다.

**운영 제약**
- KRX Open API 벌크는 **장 마감 후에야 당일 데이터를 준다.** 장중(10:40)에 조회하면 최신이 전 거래일이다. investing은 장중에도 목록을 준다.

**얻지 못하는 것**
- `stk_isu_base_info`에 업종 분류가 없다. `SECT_TP_NM`은 코스닥 소속부("우량기업부")이고 KOSPI 종목은 비어 있다. DART 캐시(`dart_corp_info`)에도 업종이 없다.
- 반면 `LIST_DD`(상장일), `KIND_STKCERT_TP_NM`(보통주/우선주)은 얻는다.

## 확정된 설계 결정

1. **당일 신고가 판별은 investing.com을 유지한다.** 교체 대상은 과거 이력뿐이다. investing은 장중에도 목록을 주고, 판별 로직을 직접 지는 검증 부담이 없다.
2. **과거 이력은 KRX Open API 일자별 벌크로 로컬에 적재한다.** 깊이 **11년**. 초기 백필 1회(약 16분) 후 하루 2콜 증분.
3. **별도 DB 파일 `data/prices.db`로 분리한다.** 가격 이력은 16분이면 재생성 가능한 캐시이고, 지켜야 할 데이터(스캔 이력·AI 분석·DART 캐시, 현재 33MB)와 수명이 다르다. 섞으면 백업 정책을 양쪽 최악에 맞추게 된다.
4. **원주가를 저장하고 보정은 이벤트 테이블로 분리한다.** 보정 로직에 결함이 있어도 이벤트만 재계산하면 되고 원본을 잃지 않는다. 이벤트는 1.4년에 537건으로 무시할 크기다.
5. **`recency_source`의 KRX 종목별 조회 경로를 전부 삭제한다.** `fetch_bars`, `CHUNK_DAYS`, 역방향 청크 루프, 빈 응답 재확인 로직이 대상이다. 존재 이유가 사라진다.
6. **신선도 창을 250 거래일에서 365 달력일로 바꾼다.** A·B·`prev_high_52w`가 모두 같은 정의를 쓰게 되고, investing의 52주 정의와 맞으며, 평화산업·코스맥스류의 경계 불일치가 사라진다.
7. **B < 365일인 종목은 `⚠ 이력 불일치` 그룹으로 분리한다.** 목록 맨 아래에 두되 신고가 카운트와 AI 분석에서 제외한다. 완전 제외하지 않는 이유는, 우리 보정이 틀렸을 때 사용자가 볼 수 있어야 하기 때문이다.
8. **로그인 클라이언트는 업종 분류 용도로만 남긴다.** 완전 제거는 업종 대체 경로(DART `company.json`의 `induty_code` 등)를 찾는 별건이며, 섹터 표기 체계가 바뀌므로 이 설계에 넣지 않는다.
9. **전 종목을 저장한다.** 우선주·리츠·스팩을 거르지 않는다. investing도 우선주를 신고가로 올리고(GS우), 벌크는 어차피 전 종목을 반환하므로 거르는 이득이 없다.

**소비 측 변경**: `src/recency_source.py`는 `fetch_bars`를 잃고 `load_bars`를 쓴다. `enrich_highs`에서 `client` 인자가 사라진다.

## 데이터 모델 — `data/prices.db`

```sql
CREATE TABLE daily_px (
    d      TEXT NOT NULL,        -- YYYYMMDD
    ticker TEXT NOT NULL,        -- 6자리
    market TEXT NOT NULL,        -- KOSPI | KOSDAQ
    high   INTEGER NOT NULL,     -- 원주가. 거래정지일은 0
    close  INTEGER NOT NULL,
    chg    INTEGER NOT NULL,     -- 전일대비. 기준가 역산에 필요
    PRIMARY KEY (d, ticker)
);
CREATE INDEX idx_px_ticker_d ON daily_px(ticker, d);

CREATE TABLE px_adjust (
    ticker TEXT NOT NULL,
    d      TEXT NOT NULL,        -- 이벤트 발생일(= 새 기준가가 적용된 첫 거래일)
    factor REAL NOT NULL,        -- 전일 실제 종가 / 당일 기준가
    PRIMARY KEY (ticker, d)
);

CREATE TABLE px_meta (
    key   TEXT PRIMARY KEY,
    value TEXT NOT NULL          -- last_loaded_date, backfill_start 등
);
```

컬럼을 6개로 줄였다. 스파이크는 10개(저가·등락률·상장주식수·거래량 포함)로 1.4년 96MB였다. 저가·등락률은 쓰지 않고, 상장주식수는 기준가 역산으로 대체되며, 거래량은 당일치만 필요한데 그것은 investing이 준다.

**용량 수치의 근거**: 이 문서의 "11년 약 780MB"는 스파이크의 10컬럼 측정치를 외삽한 값이었다. 6컬럼 실제치는 백필 완료 후 실측한 결과 **742MB**(2026-08-20)로, 예상대로 10컬럼 외삽치보다 작다.

## 수정계수 알고리즘

**검출** (`detect_adjustments`, 순수 함수). 티커의 행을 날짜 오름차순으로 훑으며:

```
기준가 = 당일 close - 당일 chg      # 당일이 출발한 가격
전일종가 = 직전 행의 close
계수 = 전일종가 / 기준가
|계수 - 1| > THRESHOLD 이면 이벤트로 기록
```

`기준가 <= 0` 또는 `전일종가 <= 0`이면 건너뛴다.

`THRESHOLD = 0.005`(설계 당시 0.02에서 하향, 2026-08-20 실측 반영). 스파이크 표본(1.4년)에서는 가장 작은 실제 이벤트가 주식배당 약 5%였고 현금배당락은 검출되지 않았지만, **구현 시 11년 전체(648만 행)로 0.5~2% 구간을 훑은 결과 실제 이벤트 253건이 발견됐다** — 56%가 12월 말 주식배당 권리락이었다. 정상 거래일은 계수가 정확히 1.0(오차 0)이라 잡음 여유가 필요 없고, 0.5% 미만의 편차는 같은 티커가 인접일에 동일한 편차를 반복하는 패턴으로 반올림 잡음임이 확인돼 그 지점을 임계값 하한으로 확정했다. 그 결과 검출 이벤트는 3,365건(구 임계값 0.02 기준 3,112건)이다.

**적용** (`apply_adjustments`, 순수 함수). 날짜 내림차순으로 누적 계수를 굴린다:

```
cum = 1.0
for i from last downto 0:
    adj_high[i] = high[i] * cum
    if d[i] 가 이벤트이면: cum /= factor[d[i]]
```

이벤트 당일은 이미 새 기준으로 표시돼 있으므로 보정 대상이 아니다. 이벤트 **이전** 날짜들만 `1/factor` 배가 된다. 링크드 예: `factor=0.2` → 이전 가격 ×5 → 396 → 1,980.

## 신선도 계산 변경 — 달력 창

`src/breakout_recency.py`의 `compute_recency(bars, window=250)`가 **거래일 수**를 쓰던 것을 **달력 일수**로 바꾼다.

```python
def compute_recency(bars: list[Bar], window_days: int = 365) -> Recency | None
```

- **A**: 과거일 j가 그날의 52주 신고가인지 = `bars[j].high >= max(high of bars in [j.date - window_days, j.date - 1일])`. 워밍업 조건은 **`bars[0].date <= bars[j].date - window_days`** 이다 — 즉 j 이전 창 전체를 덮는 데이터가 있을 때만 j를 후보로 삼는다. 조건을 만족하는 j가 없으면 A는 `None`이다.
- **B**: 정의 불변(확보 이력 전체에서 오늘 고가 이상이었던 마지막 날).
- **`prev_high_52w`**: 오늘 이전 `window_days`일 구간의 최고 고가. 그 구간을 덮는 봉이 없으면 `0.0`.

이 변경은 리뷰를 통과한 순수 모듈을 건드리므로 기존 테스트 전면 재작성이 따른다. 그 비용을 감수하는 이유는 6번 결정에 적었다.

## 리포트 변경

- `⚠ 이력 불일치` 그룹을 `GROUP_ORDER` 맨 끝(정보 없음 뒤)에 추가한다. 진입 조건은 `days_since_price_above is not None and days_since_price_above < 365`.
- 이 그룹의 종목은 `MarketStats.new_high_count`에서 제외하고, AI 분석 대상 선정에서도 제외한다.
- 상장일(`LIST_DD`)을 `daily_px`와 별도로 보관할지는 **범위 밖**으로 둔다. 현재 "상장 이후 최고" 판정은 확보 이력 길이로 추론하는데, 11년 백필 후에는 그 추론이 사실상 정확해진다.

| `prices.db`가 없거나 비어 있음 | 신선도 전 종목 `None`, 배지 생략. 스캔은 정상. 로그로 백필을 안내. `sync()`는 `last_loaded_date`가 없으면 **아무것도 받지 않고 경고만 남긴다** — 자동으로 11년 백필을 시작하지 않는다(16분짜리 작업을 `run`이 몰래 트리거하면 안 된다) |
| 백필 중단 | 이미 적재된 날짜를 건너뛰고 재개. `daily_px`에 그 날짜 행이 있으면 완료로 본다 |
| `sync()`가 당일 데이터를 못 받음(장중 실행) | 마지막 거래일까지만 적재. `enrich_highs`가 마지막 봉 날짜 != 기준일인 종목을 전부 건너뛰므로 배지가 아예 붙지 않는다(가격 가드는 2차 검사로 남는다) |
| 특정 종목 이력 부족(신규 상장) | `compute_recency`가 A를 `None`으로, 리포트가 `신규 상장` 그룹으로 처리 (기존 동작) |
| KRX Open API 401 | 명확한 예외로 중단. 키 확인·서비스 이용 신청을 안내 (기존 클라이언트 동작) |

## 리스크

**수정계수 오검출/미검출.** 원주가를 보존하므로 재계산으로 복구 가능하고, `⚠ 이력 불일치` 그룹이 이상을 눈에 띄게 만든다. 다만 **과보정은 조용히 틀린다** — 과거 고가가 실제보다 높아지면 진짜 신고가가 불일치로 분류된다.

2026-08-20 백필 후 검출 이벤트 상위 50건을 육안 확인했다. 42건이 정수배(10배 38건, 50배 2건, 25배 2건)로 전형적인 액면분할이었고, 삼성전자 보통주(005930)와 우선주(005935)가 같은 날 동일하게 50배로 잡혀 교차 검증됐다. 비정수배 8건 중 2건을 표본 확인한 결과 오리온 지주사 전환(인적분할, 20.36배)과 대규모 감자(76.14배)로 설명됐다. **설명되지 않는 건은 없었으나 비정수배 8건 중 6건은 미확인으로 남아 있다.**

**상위 50건 육안 확인은 이 위험을 해소하지 못했다(2026-08-20 최종 리뷰).** 과보정의 실제 사례는 계수가 *가장 큰* 쪽이 아니라 *가장 1에 가까운* 쪽에 있었기 때문에, 상위 50건 표본은 구조적으로 이 유형을 볼 수 없었다. 장기 거래정지가 풀리는 날 KRX가 시가 단일가 경매로 기준가를 다시 잡으면 기준가가 정지 직전 종가와 어긋나 이벤트로 잡히지만 실제로 조정된 것은 없다. 저장된 3,365건 중 **239건**이 이 유형이었다(예: `009410` 20241031 계수 0.983·정지 153일, `018120` 20190911 계수 0.9933, `477760` 20260527 계수 1.0985). 걸린 이벤트마다 이전 고가가 최대 10%까지 재환산돼, 정지 전 고점이 오늘가보다 8% 높던 종목이 오늘가 아래로 밀리고 `🏔 상장 이후 최고` 배지와 AI 프롬프트가 조용히 틀렸다.

`detect_adjustments`가 이제 **직전 행이 정지일(고가 0)이면서 계수가 1의 ±10% 이내**(`HALT_RESUME_MAX`)인 이벤트를 버린다. 두 조건이 모두 필요하다 — 액면분할도 정지 다음 날 재개되지만 계수가 50·10·5·1.8 등으로 1에서 멀다. 감수하는 위험: 10% 미만의 진짜 이벤트(예: 5% 주식배당)의 락일이 하필 정지 바로 다음 날이면 놓친다. 락일은 정상 거래일에 잡히므로 드물다. 검출 규칙을 바꾸면 `prices backfill`로 이벤트를 재계산해야 반영된다.

**용량 742MB(2026-08-20 실측).** 재생성 가능한 캐시라 백업 대상은 아니지만 디스크는 쓴다. 깊이를 줄이면 선형으로 준다(6년 약 405MB).

**장 마감 전 실행.** 벌크가 당일 데이터를 주지 않는 시각에 `run`을 돌리면 마지막 봉이 전 거래일 것이 된다. 이제 날짜 가드가 그런 종목을 전부 건너뛰므로 배지가 없는 리포트가 나온다 — 어제 값에 오늘 딱지를 붙이는 것보다 낫다. 정확한 데이터 공개 시각은 여전히 미확인이다.

**초기 백필의 5,740 요청(2026-08-20 실측 완료).** 스파이크에서 716건 연속 성공을 확인했고, 실제 11년 백필도 5,740건 요청·5,392 거래일 적재·6,481,499행·12.1분으로 실패 없이 완료돼 검증됐다. 이어받기가 되므로 중단돼도 손실은 없다.

## 테스트 전략

- **`adjust.py` 순수 함수** — 합성 데이터로 액면분할(계수 10)·병합(계수 0.2)·무상증자(계수 1.8)·주식배당(계수 1.05)·이벤트 없음·거래정지 구간 포함·임계값 경계.
- **`apply_adjustments`** — 이벤트 당일은 보정 대상이 아님, 다중 이벤트 누적, 이벤트 이후 날짜 무변경.
- **`loader.load_bars`** — 임시 DB로 정상 조회, 이력 없음 → `None`, 보정 적용 확인, 기간 필터.
- **`backfill`/`sync`** — 페이크 fetcher로 재개(이미 적재된 날짜 건너뜀), 빈 응답(휴장) 처리, `px_meta` 갱신.
- **`compute_recency` 달력 창** — 기존 8개 케이스를 달력 기준으로 재작성 + 250거래일/365달력일이 갈리는 경계 케이스.
- **리포트** — `⚠ 이력 불일치` 그룹 진입/미진입, 카운트 제외, AI 대상 제외.
- **회귀** — 기존 전체 스위트 248 통과 유지.
